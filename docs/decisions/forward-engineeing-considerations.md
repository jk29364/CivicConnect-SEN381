### 3. Forward Engineering Considerations (M2 Updates)

*This register identifies seven downstream lifecycle concerns flagged during M1 to guide upcoming architecture and construction without premature design decisions. M2 resolutions have been added to track the evolution of the PED.*

| # | Lifecycle Concern | Why It Matters Now (M1) | What It Influences Later (M2–M4) | Missing Information / M2 Status | Risk of Ignoring |
| :-: | :--- | :--- | :--- | :--- | :--- |
| **FEC-01** | **Authentication & Authorization Model** | Shapes NFR-002 and enforces distinct privilege boundaries between residents, maintenance staff, and managing agents. | Milestone 2 architecture decomposition and Milestone 3 access-control middleware. | **[M2 Resolved]:** Implemented stateless JSON Web Tokens (JWT) passed via the `Authorization: Bearer` header (ADR-INT1). | Extensive schema and route restructuring if access control is retrofitted onto an open prototype. |
| **FEC-02** | **Deployment Platform Boundaries** | Free-tier resource limits restrict the realistic concurrency targets we can commit to in our Non-Functional Requirements. | Milestone 2 technology selection and Milestone 4 production operations and costing. | **[M2 Resolved]:** Backend and frontend deployed via free-tier cloud containers (Render/Vercel); database hosted on Supabase (ADR-STACK1). | Overpromising availability metrics that crash during live demo evaluation under load. |
| **FEC-03** | **Data Retention & Audit History** | Estate dispute resolution requires tamper-evident, historical tracking of all ticket status changes (NFR-003). | Milestone 2 relational persistence design (e.g., append-only log vs. mutable row updates). | **[M2 Resolved]:** Audit trail is preserved using PostgreSQL's native relational integrity and atomic multi-row transactions (ADR-DATA1). | Total loss of historical auditability if status changes overwrite previous ticket states destructively. |
| **FEC-04** | **Automated Testing & CI Integration** | Automated test pipelines execute in Milestone 3, but requirements must be written with quantifiable acceptance criteria now. | Milestone 3 CI pipeline construction and branch merge quality gates. | The specific assertion libraries and mock test harnesses supported by the stack chosen in M2. | Requirements phrased in vague terms that cannot be validated by automated assertions. |
| **FEC-05** | **System Observability & Monitoring** | Managing agents require automated tracking of overdue service requests (FR-008), requiring internal health monitoring. | Milestone 3/Milestone 4 operational readiness, structured telemetry, and failure alerts. | Minimalist logging patterns suitable for deployment on low-overhead student environments. | Complete inability to diagnose runtime faults or demonstrate operational readiness in Milestone 4. |
| **FEC-06** | **Scalability Expectations** | NFR-005 defines performance baselines that must reflect Wonderpark Estates' realistic resident population and unit counts. | Milestone 2 architectural partitioning (monolith vs. decoupled modular services). | Empirical baseline of peak concurrent request volume during estate emergencies (e.g., water outages). | Committing to an under-provisioned architecture that cannot handle peak residential filing surges. |
| **FEC-07** | **Data Migration & Disaster Recovery** | If database schemas evolve or hosting platforms change, an export and restoration pathway is required. | Milestone 3/Milestone 4 deployment, backup scripting, and database migration routines. | Native automated backup and point-in-time restore capabilities provided by free-tier databases. | Irrecoverable loss of baseline seed data and test records late in the academic project cycle. |
